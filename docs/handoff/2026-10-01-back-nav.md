# 2026-10-01 back-nav — Back link + browser back/forward for results pages (single task, UI only)

## Decisions
- A page is committed to history when a non-append search SUCCEEDS (`commitPage()` in `search()`), not at `run()`. So failed/superseded searches leave no entry and no placeholder page ever needs a re-run on restore.
- `run()` snapshots the page being left (`leavePage()`) before touching `S.base/S.query/S.start`; `S.hist.fresh` marks "new page loading" so a second `run()` or a popstate never snapshots half-updated live state.
- Form state is the DOM captured at run time (`readInputs()`, `S.inputs`), not rebuilt from `S.query`: `#bib` and the description inputs of a bib page are not in the query.
- Restore reuses the existing guards: `++S.seq; ++S.nseq; retireBulk(); closeModal()` — no new stale-response flags. Restore never calls `search()`; a bare `refreshNear()` only if the captured page had no nearby list but nearby is now on.
- Entries are keyed by page id in `history.state {hid, pf}`, not by array index (cap shifts indices). `hid` is random per history object, so entries from before a reload/profile/race clear (or another document session) are ignored.
- First page of a history uses `replaceState` (browser-back from it leaves the app; matches "Back hidden on the first page"); later pages `pushState`, which drops browser forward entries like the in-memory truncation does.
- Back link click = `history.back()` (one restore path via popstate). Exception: while a new page is loading it cancels that load and restores the page being left (that page has no browser entry yet; label names it). A failed new search does the same (`cancelFresh()`), so the screen never shows old cards under the new query.
- Link lives in `.summary` above `#summary` (which is rewritten by summary/welcome/picker/loadMe); shown only on the Search view.
- New results page now starts scrolled to the top (before, the old scroll offset carried over); needed so "scroll restored" is distinguishable. Tab-switch scroll is remembered in `S.searchScroll` since Search and My photos share the `main` scroller.
- Cards are repainted from current `S.labels` by `card()` as before; snapshots hold copies of `results`/`near` arrays (Load more mutates `S.results`).
- No keyboard shortcut added; Alt+← is the browser's.

## Rejected
- Push at `run()` time and re-run on restore of an unfinished page: extra /search and reshuffle, plus dead entries on failure.
- Abort the in-flight fetch on Back (AbortController): would undim the grid sooner but changes `post()`/`api()` error paths; guards already make the response harmless.
- Back link calling restore directly and rewriting `history.state`: breaks forward/back index parity.
- Reconstructing inputs from `S.query`; hash/URL per page (not needed, brief says none).

## Assumptions
- `history.state` survives within the document and popstate is delivered for same-document entries (verified in jsdom only; the orchestrator's real-browser E2E should confirm).
- Search results/near lists are plain JSON, so shallow array copies suffice.

## Deferred
- While a slow search for a page you left is still in flight, the restored grid stays dimmed and Find more/Load more disabled until it returns (busy counter is global). Safe: the response is dropped.
- After a profile/race switch the browser still has the old entries behind the current one; Back on them does nothing (ignored by `hid`).
- Failed-search recovery (`cancelFresh`) forces the Search view if the user switched tabs meanwhile.
