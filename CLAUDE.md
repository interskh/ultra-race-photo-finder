# photofinder — agent notes

Personal tool to find the user's own photos in race-photo galleries (faces often covered, night races) by clothing, bib, time, photographer and scene. Local only; developed on a 16 GB Apple Silicon Mac. Published as `ultra-race-photo-finder` (AGPL-3.0-or-later); the package and CLI stay `photofinder`.

## Layout
- `src/photofinder/sources/yipai.py` downloader (`refusal()` guards registered order ids) · `sources/{base,common}.py` + `sources/{pailixiang,xxpie,photoplus}.py` paced album downloaders for the other platforms; each platform module has `site_link` (Open on site; dispatcher `sources.site_link`) · `races.py` race registry (`data/races.json`, race/album dirs, album URL parsing) · `race_import.py` one-time legacy collection → race move · `index/stages.py` indexing stages · `models.py` model loaders · `search.py` scoring/filters · `nearby.py` same-photographer neighbouring shots of confirmed photos (roll order, best match, dedupe) · `evaluate.py` bib-based recall eval · `originals.py` full-size originals job (yipai: fresh signed URL by file name; photoplus: `photoplus.Locator` bisects the album listing by shot time; pailixiang/xxpie: `Locator` file-name search; CSV, zip) · `web/app.py` + `web/static/index.html` UI · `cli.py` entrypoint (`photofinder index|search|eval|serve|download|race add|race import|album add`; `index|search|eval|serve` take a race slug or a directory) · `scripts/download.sh <race> [album-key]` detached race download · `scripts/download_yipai.sh <orderId>` legacy single-gallery download.
- Data (gitignored) under `data/`: `races.json` (registry, CLI-written), `races/<slug>/{index.sqlite, index.lock, download-console.log, albums/<platform>-<id>/{photos/, manifest.sqlite, download.log, .download.lock}}`, `yipai/<orderId>/{photos/, manifest.sqlite, index.sqlite, download.log, index.log}` (legacy location), `backups/` (index backups from `race import`), `subsets/` (symlink subsets for experiments: `first2000`, `race925`, `scenemix`), `models/` (all weights/caches), `exports/<slug or collection>/<profile>/{originals/, photos.csv}` (per saved person; `exports/screens/` holds E2E screenshots).
- The data root defaults to the checkout's own `data/` (`config.DEFAULT_DATA_ROOT`), so a git worktree has an empty one. `PHOTOFINDER_DATA_ROOT` overrides it for rehearsals; `PHOTOFINDER_MODELS_DIR` overrides the weights dir (default `<checkout>/data/models`; from a worktree point it at the main checkout's `data/models`). `serve.lock` follows the data root, so a server under another root can't see the real one — the one-server rule still applies.

## Rules
- Everything large lives under the data root (on this machine the checkout is on the external disk) — photos, indexes, weights (`config.setup_model_env()` points HF/torch/ultralytics caches at `data/models`). Never download into `~`.
- uv only. The shell sets `UV_FROZEN=1`; lock-changing commands need `UV_FROZEN=0 uv add ...`.
- Don't hammer yipai360: keep the downloader's pacing (6 workers, page delay, breaker). The downloader fetches only free 1920px previews; originals are fetched only for marked photos by `originals.py` (1 lookup per 6 s — the file-name search is rate-limited at ~10 per 30 s and answers HTTP 500 when exceeded; the job waits 60/120/240 s before giving up; one job per collection).
- Top up a race with `scripts/download.sh <race>` (rerun = resume/top-up). `download_yipai.sh` refuses an order id that is registered in a race.
- Never modify a collection that a running downloader/indexer is writing; experiment on `data/subsets/*`. `index` holds a per-collection lock.
- `race import` refuses while the collection's `index.lock` / `.download.lock` or `data/serve.lock` is held. It takes no subset lock: don't run it while an indexer runs on a `data/subsets/*` collection, because their photo symlinks are re-pointed at the end. Start nothing (download, index, serve) until it prints its summary; afterwards `index <slug>` must scan 0 new photos. Interrupted → rerun the identical command (forward recovery).
- One heavy model job at a time (16 GB unified memory); the memory guard throttles on system pressure. `index` runs each model stage in a spawned child capped at `--max-memory` (default 4096 MB) and restarts it fresh at the cap (content-dependent leak). Measured floors and why 2 GB isn't reachable: `docs/handoff/2026-09-29-index-memory-cap.md`.
- `photofinder serve` with no argument opens the race picker (one race loaded at a time; switching unloads the previous); `serve <slug>` preloads that race; `serve <dir>` serves a directory (e.g. a subset) as the only race. Originals download from all four platforms (yipai360: file-name search, 1 per 6 s; photoplus: one listing request per 2.5 s, bisection by shot time; pailixiang and xxpie: one file-name search per photo, >=2.5 s apart; pailixiang's copy has no EXIF); a platform whose API is down fails only its own photos.
- One photofinder server at a time, machine-wide — enforced by you as well as the lock: `serve.lock` lives in the data root, so a server started from a worktree (whose default data root is its own `data/`) or under another `PHOTOFINDER_DATA_ROOT` does not see the main checkout's server. `serve` holds `<data root>/serve.lock` (pid, URL, and `race picker`, `race picker (<slug>)` or the directory) and refuses a second start before loading anything. For dev/E2E, stop the user's server and restart the one server on the new code (only when the user wants it running); never start a second server beside it. Use a subset (`data/subsets/race925`) when the full index isn't needed.
- Server models run in a spawned child process (`web.app.ModelWorker`, one `ProcessPoolExecutor(1)`), stopped after `IDLE_UNLOAD` (300 s) without model work; never unload/reload models inside a long-lived process (each cycle keeps ~1 GB, measured). `serve` sets `models.half_precision` (SigLIP2 `pure_fp16` on MPS); indexing stays fp32. `GET /api/models` drives the UI's loading indicator. Tests swap in a thread pool (`test_web.no_real_models`). Details: `docs/handoff/2026-09-28-model-memory.md`.
- Private data (people's and photographer names, the user's own photo ids/file names, account ids, site tokens) never goes into code, fixtures, docs or commit messages; the repo is public. Synthesize fixture values.
- Site keys (pailixiang web-client key, photoplus salt) are never committed: `sources.common.site_key` reads env vars or `~/.config/photofinder/site-keys.json` (private copy in `data/dev-notes/`).
- Tests: `uv run pytest -q` (655 passed + 1 opt-in real-model test, `PHOTOFINDER_REAL_MODELS=1`, as of 2026-10-01).
